# 注册中心升级与部署说明

## 调用身份与所有权

直接 mTLS 部署建议显式配置：

```properties
enable_https=true
verify_client=true
owner.isolation.enabled=true
owner.identity.mode=certificate
owner.validation.mode=strict
```

使用 `python -m agent_registry.start` 启动，它安装 TLS 适配器，把经过验证的对端证书
交给所有权校验；integration listener 使用同一适配器。自定义启动器需要安装该适配器。
客户端自行填写的身份头不能替代经过验证的证书。

在终止 mTLS 的代理后部署时，显式选择 `owner.identity.mode=trusted_proxy`，
`owner.trusted.proxy.ips` 填实际建立连接的代理地址。代理必须清除外部传入的
`X-SSL-Client-DN`，只写入它已验证的身份，并阻止客户端直接访问应用端口。
`forwarded_allow_ips` 只管理转发 IP，不代表已完成所有权认证。`owner.trusted.proxy.ips`
绝不能写 `*`；`forwarded_allow_ips=*` 仅适用于自身终止 TLS 且会重写转发头、代理地址不固定的
平台（如 Cloud Run），普通反向代理不要这样配。该值不要加引号（写成
`forwarded_allow_ips=127.0.0.1`）：读取器只去空白，uvicorn 逐项按字面比较，写成
`"127.0.0.1"` 会导致任何代理都不被信任（代理头被静默忽略）。身份来源和代理列表支持
环境变量 `REGISTRY_OWNER_IDENTITY_MODE`、`REGISTRY_OWNER_TRUSTED_PROXY_IPS`。

开启隔离后，无 owner 历史记录在已发布时仍可被发现，但不能由调用者任意修改。
先备份数据库，再逐条审核并由受控管理迁移分配经过验证的 owner；没有“首个调用者自动认领”机制。
本次保留 CN owner 兼容性，尚未把全部历史 owner 迁移为新的 issuer/subject 主体 ID。

## 审批可见性与事件

`registered` 待审批 Card 不进入公开发现结果或语义选择提示词。审批通过产生
`AGENT_REGISTERED`；已发布记录下架产生不含完整 Card 的 `AGENT_DEREGISTERED`。
修改 Card 不改变审批状态，重复设置待审批状态不产生公开更新事件。
健康查询也不公开待审批对象；已发布但离线的对象仍可用于运维监控。

新公开事件携带 `data.discovery_public=true`。没有此标记的历史 outbox 事件，
在 `/changes` 和 webhook 中转换为 `SYNC_REQUIRED`，保留事件 ID、版本号，设置
`data.requires_snapshot=true`，避免继续暴露旧待审批 Card。消费方应重新获取已发布 Card
列表并替换发现缓存，不再应用旧 payload；分页游标仍正常前进。当前列表接口不是带一致性游标
的原子快照，初始化并发一致性仍属于后续游标改造范围。

webhook 仍为尽力投递，但**每个订阅者现在各有独立交付状态**（SQL 模式下是 `registry_event_deliveries`
表里的一行，一个订阅 × 一个事件；文件模式写同目录的旁挂文件），因此慢订阅不会再被快订阅"代表完成"：
重启恢复只重放该订阅者尚未收到的部分，事件会一直保留到所有订阅者都不再需要它。**失败现在有持久且有界的重试**：
失败行由周期性扫描（启动时也会扫一次，因此崩溃不会丢掉这次重试）重新入队，直到该交付用满
`broadcast.delivery.max.attempts`（默认 5）次尝试，扫描间隔 `broadcast.delivery.retry.interval`（默认 60 秒）。
预算用尽后该交付在内部交付账本中保持 `delivery_failed`。`/changes` 仅提供事件内容用于对账，
不返回某订阅的交付状态或 attempts，不能据此查询 webhook 是否投递失败；永久不可达的目标不应无限重试。
仍未提供：恰好一次交付（重试可能重复投递，请按 `event_id` 去重）、单次扫描间隔之外的逐次调度，
以及分布式租约（多实例共用同一 outbox 时，各实例都会独立扫描同一失败行）。
消费方仍需保存游标、支持对账并按 `event_id` 去重；不要把某个订阅者的交付状态当作其他订阅者已确认。

同批事件按版本顺序发送，但持久重试可能让旧失败事件晚于新事件到达。消费方除了按事件 ID 去重，
更新发现缓存时还应忽略陈旧 `registry_version`，并通过 `/changes` 按序对账；串行 worker 不保证跨重试的严格顺序。

批量发送窗口按版本顺序保留每个事件 ID，同一 Agent 的多次变更也不再用新 payload 覆盖旧持久事件。
SQL 交付变更与事件汇总在同一事务中提交；启动恢复直接读取逐订阅 pending 行，即使遗留汇总状态陈旧也不会漏掉。
文件模式也恢复账本中的 pending 行，但不承诺跨文件原子事务。
健康监控的列表、历史和 SSE 只过滤审批公开资格，不使用任务发现的“不健康结果隐藏”策略，确保离线告警可见。

版本号改为由单行计数器 `registry_event_counter` 分配，且与事件插入在同一事务内提交，
因此该行的锁持有到提交、**版本顺序 = 提交顺序**：按 `since=<版本号>` 拉取的消费方
不会再漏掉"先分配、后提交"的事件。该保证适用于 SQL 持久化模式（postgresql、gaussdb、
mysql）。这是版本分配机制的性质，不代表支持多实例部署：注册中心仍按单实例部署对外说明，
请勿据此在同一数据库上运行多个实例。由于该行是串行点，事件写入按提交逐个串行。
文件模式与内存模式仍为单实例分配。升级时会用现有最大版本号播种计数器；
若绕过 outbox 直接写 `registry_events`，计数器会落后（`registry_version` 的唯一索引仍会拒绝重复版本）。

## 回调目标和图库

创建订阅前必须配置 `broadcast.callback.allowlist`，例如
`operator.example.com,authorized-internal.example`；空列表会拒绝新订阅，也会阻止旧订阅继续发送。
HTTP 另需显式设置 `broadcast.allow.http.callbacks=true`。不接受 URL 内嵌用户名/密码，
不跟随重定向，每次发送前重新校验目标权限。电信内网回调可以显式授权，不支持主机通配符。

主机白名单不等于 DNS 地址固定；部署需控制 DNS 和服务网络出口，连接时 IP 固定仍待后续实现。
不要把已授权域名的解析权交给不可信调用者。

预埋图库 API 默认返回 404。启用时配置 `knowledge_graph.enabled=true`，或
`REGISTRY_KNOWLEDGE_GRAPH_ENABLED=true`，并提供 Neo4j 凭据和独立图库权限。
认证插件的 Principal 可以携带 `knowledge_graph:read` / `knowledge_graph:write` scope；
也可用 `knowledge_graph.allowed.owners` 或 `REGISTRY_KNOWLEDGE_GRAPH_ALLOWED_OWNERS`
配置已验证 owner 为读写管理员。默认匿名认证没有图库权限。
Neo4j 不参与 AgentCard 权威存储和基础发现；当前通用图库 API 未实现租户隔离。

## 签名、模型错误和标签

注册/更新通过异步路径等待 JKU 验签；任一受信有效签名即可通过，前面的缺失密钥或畸形签名
不会阻断后面的有效签名。RSA JWK 使用 `n/e`，EC ES256 使用 P-256 与 `x/y`，JWK 的 `alg`
可省略。JKU 仍需独立的主机白名单和 HTTPS；禁止重定向，实际流式响应最多 1 MiB，
未提供 Content-Length 的响应同样受限。

语义查询模型未配置、调用失败或输出无法解析时返回 503；正常无匹配返回 200 空列表。
普通日志和查询审计不写任务正文；精确查询和 CRUD 不依赖可用模型配置。

标签改名会同步 Agent 标签引用；核心删除路径会把该标签从所有 Agent 上解绑。CLI/内部服务保留
既有保护：删除仍被使用的标签会被拒绝并返回受影响的 Agent 列表，运维需先解绑；只有编程调用
（以及改名）会走到解绑逻辑。SQL 将标签、引用和已发布 Agent 的更新事件放入同一 UoW，
事件写入失败时回滚。文件存储仍不具备跨文件原子性，只面向本机/小规模使用。
待审批 Agent 的标签变化不产生公开事件。

语义查询现在在两条候选分支上都区分"确实没有候选"与"模型不可用"：没有任何候选通过可见性过滤时，
直接返回空结果、不再调用模型（此前向量分支会把空候选交给模型选，模型正好不可用时就把"无匹配"变成 503）；
嵌入服务失败统一报 503（`SemanticSearchUnavailable`），不再逃逸成未处理的 500。记录存储分支此前已是此行为。

**任务发现**的可见性规则现在由两个 HTTP 端口共用：集成端口此前自己内联了一份判断（状态字符串 + 健康隐藏），
与主端口的 `_is_discoverable()` 并存、可能给出不同答案，现已统一调用同一谓词。健康监控的列表/历史/SSE
不使用这条谓词（用途区分见本节前面的健康监控说明）。`get_status()`
对"记录存在但状态列为空"的历史行归一化为 `published`，与存储层 `COALESCE(status, 'published')`
的过滤口径一致——列表能返回的遗留行不会再被判成未发布；**记录不存在仍返回 None**（仍不可见），
"没有这张卡"与"遗留的已发布卡"保持可区分。

旧 `use_vectordb=true` 仍是替换权威存储的实验模式；本次尚未实现 SQL 权威库回表的 N 选 X、
投影修订号、索引重建及迁移。**本次的行为变化**：该模式下不再回答它回答不了的问题——审批状态、
所有权、标签（含标签实体本身的增删改查）、Card 元数据、Card 列表，以及必须向变更流宣告的更新/删除操作，
现在统一返回 **HTTP 503**
（`registry.use_vectordb=true replaces the authoritative record store ...`），
而不是返回空列表、默认状态或"改了但没有任何订阅者知道"的静默成功。注册与按主键精确读取仍可用，
便于运维先把数据灌进集合。可设 `startup.strict.storage=true` 让该模式直接拒绝启动。
要求审批与所有权能力一致的部署应保持 `use_vectordb=false`。

## 心跳归属

开启 `owner.isolation.enabled=true` 时，心跳接口要求身份与卡片 owner 一致（身份不可验证
返回 401、非 owner 返回 403，与修改/删除同一套策略）。心跳是"这张卡还活着"的声明：它决定
`heartbeat.hide.unhealthy.results` 是否隐藏死卡、离线 TTL 是否自动注销，并可发布公开的健康
恢复事件——此前任何通过认证的调用者都能替任意卡片做这个声明。若部署中由单个监控进程代所有
Agent 上报，应保持隔离关闭，或为监控进程配置各 owner 的凭据。隔离关闭（默认）时该接口行为
与旧版本完全一致。

## 容器与前端

容器镜像默认启用 HTTPS、mTLS 和所有者隔离，需要挂载证书并配置部署策略。关闭监听器 HTTPS
不会自动关闭所有者隔离和 Card 完整性校验。compose 是显式的本机开发配置：关闭客户端认证，
只绑定 `127.0.0.1`，不能通过放开端口绑定把它直接变成生产配置。

探针使用 `python -m agent_registry.healthcheck`，遵循服务端 HTTP/HTTPS 与 CA 配置，
不关闭证书验证。mTLS 模式需提供 `REGISTRY_HEALTHCHECK_CLIENT_CERT`、
`REGISTRY_HEALTHCHECK_CLIENT_KEY`，建议使用单独的有读取权限的探针身份。
`REGISTRY_HEALTHCHECK_HOST` 默认 `127.0.0.1`，证书使用其他 SAN 时需配置可访问且匹配证书的主机名。
注意：本文档给出的证书不设置 SAN，因此在 HTTPS 模式下用默认的 `127.0.0.1` 探针**无法**通过校验
（IP 字面量只能匹配带 `iPAddress` SAN 项的证书）。请把 `REGISTRY_HEALTHCHECK_HOST` 设为与证书 CN
一致的名字（例如 `agent-registry`），或为探针证书签发覆盖探测主机的 SAN。
当前探针检查发现 HTTP 路径，不是逐组件独立就绪检查。

前端遵循保存的 HTTPS 设置，默认继续使用同源访问；HTTPS 页面要求 HTTPS 后端地址。
测试、检查和构建分别为 `npm test`、`npm run lint`、`npm run build`。
